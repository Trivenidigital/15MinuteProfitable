2. The Analysis Cycle

Each cycle follows this exact sequence. The agent changes at most ONE parameter per cycle to maintain clean signal.

Step 1: Harvest Data

SSH into server. Copy trades.db locally or run SQL queries via SSH. Pull recent log tail for error context.

Step 2: Measure Performance (since last change)

  • Funnel metrics: Markets observed → Opportunities found → Risk approved → Executed → Profitable
  • Per-strategy: Win rate, avg profit, trade count, rejection rate
  • Market outcomes: UP/DOWN/FLAT distribution per asset, per hour-of-day
  • P&L: Net simulated profit, max drawdown, Sharpe-like ratio
  • Near-miss analysis: How many opportunities were within 1 tick of the threshold?

Step 3: Diagnose the Biggest Bottleneck

Where in the funnel is the biggest drop-off? That determines what to tune.

BottleneckSymptomLikely Fix
No opportunities found0 rows in strategy_decisions with decision="opportunity"Lower thresholds (spot_move, odds_lag, min_profit_margin)
All rejected by riskHigh % of "risk_rejected" decisionsWiden risk limits or fix overly conservative checks
Executed but losingTrades happen but net P&L is negativeTighten entry criteria, adjust stop-loss/take-profit
Profitable but too fewGood win rate but only 2 trades/dayLoosen thresholds slightly, enable more strategies
Wrong direction callsWin rate < 45%Increase confirmations, widen dead zones, check spot lag correlation

Step 4: Hypothesize & Change ONE Parameter

Pick the highest-leverage parameter for the diagnosed bottleneck. State the hypothesis clearly before changing.

Step 5: Apply Change

SSH → update /opt/btc15minutebot/.env → systemctl restart btc15minutebot

Step 6: Document (in this file)

Add an entry to the Experiment Log below with: timestamp, parameter changed, old→new value, hypothesis, baseline metrics.

Step 7: Wait for Observation Period

Minimum observation per change (see cadence rules below). Do NOT make another change until the period ends.

Step 8: Evaluate Impact

Next cycle starts here. Compare metrics post-change vs pre-change. Mark experiment as KEPT or REVERTED.

Safety Rails

  • One parameter per cycle. Never change 2+ things at once.
  • Revert on degradation. If a change makes metrics worse after full observation period, revert immediately.
  • Bounded changes. No parameter moves more than 50% from current value per step.
  • Minimum sample size. Need 20+ observations (trades or market windows) before drawing conclusions.
  • Never disable risk limits entirely. Can widen them, never remove them.
  • Log everything. Every change, every revert, every metric snapshot goes into this file.
Statistical significance matters. With 4 assets × 4 windows/hour = 16 outcomes/hour, we get ~384 market windows per day. But actual trades will be much rarer. Don't over-react to small samples. Use at least 20 trades (or 100 market windows) before concluding a parameter change helped/hurt.

6. 7-Day Game Plan

Day 1: Baseline & Enable Data Collection

  • Deploy Phase 1 observability code to server
  • Verify strategy_decisions, spot_snapshots, market_outcomes tables are populating
  • Let bot run with current config for 24h to establish baseline metrics
  • Record baseline: opportunities/hour, rejection rate, trade count, P&L

Day 2: First Strategy Activation + Tune

  • Analyze baseline data: what's the funnel bottleneck?
  • If no opportunities found → enable price_lag strategy, tune entry thresholds
  • If opportunities found but all rejected → investigate risk rejection reasons, loosen as needed
  • Make 1-2 parameter changes (12h observation each)

Day 3-4: Iterate on Active Strategies

  • Evaluate Day 2 changes. Keep or revert.
  • Enable resolution_sniper if price-lag is generating data
  • Tune exit parameters (stop-loss, take-profit) based on observed P&L curves
  • Tune dead zones based on time-of-day patterns in market_outcomes
  • Target: 2-3 parameter changes per day (8h observation each)

Day 5-6: Optimization & Multi-Strategy

  • If individual strategies show edge, enable parallel_strategies
  • Fine-tune sizing (order_size, kelly_fraction) based on observed variance
  • Analyze per-asset performance — are some assets more predictable?
  • Consider disabling strategies that show consistent negative edge
  • Target: 3-4 parameter changes per day (6h observation each)

Day 7: Evaluate & Decision

  • Compile full 7-day performance report
  • Calculate: net P&L, win rate, Sharpe ratio, max drawdown
  • Compare final config vs Day 0 baseline
  • Decision point: Is the bot ready for live trading?
  • If not profitable: document what was learned, plan next sprint
  • If profitable: discuss moving to live with reduced position sizes
